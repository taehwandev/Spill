# Detailed ARD: Release Automation and Distribution Site

## Architecture Summary

The release path remains script-first: GitHub Actions delegates packaging to `scripts/package-release.sh` so local and CI releases share the same bundle creation logic. GitHub Pages serves static files from `docs/`, using stable `latest/download` asset names generated by the release workflow.

## Decisions

### D1: Script-First Release Workflow

Decision:

Use the existing package script from GitHub Actions instead of duplicating packaging logic in workflow YAML.

Rationale:

One package path reduces drift between local verification and CI releases.

Alternatives considered:

- Reimplement packaging in workflow steps. Rejected because it would duplicate signing, notarization, and DMG logic.

### D2: Optional Developer ID Signing

Decision:

Run ad-hoc signing by default and enable Developer ID signing/notarization only when repository secrets are present.

Rationale:

The repo can produce test releases without Apple credentials, while maintainers can add credentials later for public Gatekeeper-friendly releases.

Alternatives considered:

- Require Apple signing secrets for all releases. Rejected because it would block open-source test artifacts.

### D3: GitHub Pages Static Site

Decision:

Host the distribution site from `docs/` using GitHub Pages Actions.

Rationale:

This avoids external hosting and keeps download links close to GitHub Release assets.

Alternatives considered:

- External marketing site. Rejected as unnecessary for the current distribution need.

## Modules Affected

- `.github/workflows/release.yml`
- `.github/workflows/pages.yml`
- `docs/index.html`
- `docs/styles.css`
- `docs/assets/spill-icon.png`
- `README.md`
- `.agents/runs/release-automation-site/*`

## New Types / APIs

No Swift APIs are added.

## Data Flow

```text
git tag or workflow dispatch -> GitHub Actions -> package-release.sh -> release artifacts -> GitHub Release -> GitHub Pages download links
```

## Permissions

- Accessibility: unchanged.
- Screen Recording: unchanged.
- Network: GitHub Actions uses GitHub Release and Pages APIs.
- File system: workflow writes build artifacts on the runner.

## Failure Modes

- Missing or incomplete signing secrets fail only when a signing path is requested.
- Notarization failure stops the release workflow before assets are published.
- GitHub Pages links may 404 until the first release uploads stable asset names.
- Apple Developer credentials are still required for Gatekeeper-friendly public distribution.

## Performance Notes

Release workflow duration is dominated by Swift build, DMG creation, and optional notarization. The static site has no app runtime cost.

## Test Strategy

### Automated

- `./scripts/package-release.sh`
- `codesign --verify --deep --strict --verbose=2 .build/Spill.app`
- `hdiutil verify .build/release-artifacts/Spill-2026.20.1-macos.dmg`
- `python3 .agents/scripts/workflow.py verify`
- `git diff --check`

### Manual

- Inspect the static site in a browser.
- Confirm release asset links target the expected GitHub Release URLs.

## Implementation Split

| Task | Owner | Files | Can run parallel? |
| --- | --- | --- | --- |
| Release workflow | builder | `.github/workflows/release.yml` | yes |
| Pages site | builder | `.github/workflows/pages.yml`, `docs/*` | yes |
| Documentation and verification | builder | `README.md`, run docs | no |

## Risks

- GitHub-hosted macOS runner images can change available Xcode versions.
- Notarization cannot be fully verified locally without Apple Developer credentials.
